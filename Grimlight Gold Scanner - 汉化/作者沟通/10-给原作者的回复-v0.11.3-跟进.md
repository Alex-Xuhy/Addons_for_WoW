## 第二部分：国服评分适配提案（随短邮件发出，或作为附件）

```
CN launch adaptation proposal (for discussion)

1. Loot-roll signal (need / greed)
The game exposes need rolls (1044) and greed rolls (1043), both readable on
CN (our test character: 14 need / 53 greed). Their ratio — need / (need +
greed) — is a simple, descriptive signal for "need on everything" behaviour.
We think it would be very useful to players and would help clean up the game
environment. It should read as a hint, not a verdict: show both counts and the
need share once the combined total passes a small threshold; lifetime counters
and group composition matter. This is the one feature we would most like to
see in a later version.

2. HUD hover label
The hover currently reads "GGS · GrimlightDepot.com". The URL is useful credit
and is already in the report footer and About; on the CN client the tooltip is
tight. Could the hover show just "GGS" and leave the URL to the report/About?
We are not asking to remove credit from the add-on, only from the two-line
hover.

3. Missing data questions
3.1 On the CN client, the native statistics panel shows "--" for most wealth
statistics; only the two auction counts (postings 329, purchases 330) return
values. The auction gold counter (919) has never returned a value on any of
the three characters we tested. Could this be a GGS reading issue, or a
server-side gap? Will 919 be available after launch?
3.2 Spending is mostly missing: travel (1146) reads, but postage/barber/
respec are often unreported, and repairs / auction spending / potions have no
verified IDs. Will the missing spending block be available after launch?
3.3 On my own report I see a 5-gold gap, and my auction income is certainly
higher than the panel shows; auction coverage is marked incomplete. Could this
be because 919 is missing, or because the income counters are a rolling window
rather than lifetime? Our earlier sample looked like ~6 days (total = loot +
quest + vendor; total / daily ≈ 6.04 days). If the counters are windowed,
comparing income to the lifetime peak is misleading. Can you confirm the time
basis, and show it in the report? If 919 stays unavailable, could the
completeness rule treat it as structurally unavailable, so the gold verdict
can still be computed from the other four counters and labeled "auction not
counted"? Right now the verdict is permanently "partial statistics" on CN.

4. Scoring adaptation for CN
4.1 CN context and weight adjustment
GDKP ("gold bid") runs, many solo/pug players, and world/pug raids are
expected to be far more common than in the US. GDKP payouts are direct trades;
trades and mail are not itemized. A legitimate raider who receives a large
payout will show low coverage and a large "unexplained" gap. The missing 919
biases coverage downward further. Coverage is a good exculpatory signal (high
coverage is reassuring) but a poor suspicion signal in CN (low coverage is
expected). We suggest:
- lower coverage and treat it asymmetrically: high coverage can add; low
  coverage should be neutral when the missing income is structural; if a
  counter is structurally unavailable, the factor should abstain and lower
  confidence, not score low;
- make wealth-for-level the primary suspicion axis, but first fix the
  baseline: peerMin 10 (max level 20), log-ratio + percentile, an absolute
  floor, and an exact max-level band separate from 55–59;
- keep unexplained rises secondary; GDKP sellers produce the same pattern;
- starting weights: coverage 10, unexplained rises 25, wealth for level 30,
  activity 25, firsthand 10 (to calibrate after launch).
The consistency score itself is a real step forward — complete and logically
coherent; this is about keeping it usable in a different economy, not
weakening it. Exposing RMT remains the bottom line.

4.2 The epic mount / advanced riding saver problem
On this server the epic mount is cheap but the advanced riding skill is the
expensive part (~1000G). A legitimate saver can therefore show a peak near
1000G, which looks like a GDKP buyer on a single axis. Our ideas:
(i) Vendor transactions. Can spending include purchases from vendors? The
statistics list has 921 "gold from selling to vendors" but no verified "gold
spent at vendors"; for other players, purchases are not observable; for
oneself, a wallet difference could approximate it. Is there a path?
(ii) Advanced riding detection. Is there a way to tell whether a player has
learned the advanced riding skill? There is no InspectSkill API we can find;
mounts owned (339) might be a weak proxy if it is readable for other players.
Current gold holdings would help only for oneself, and bank alts can split
the gold.
(iii) A peak threshold. A saver's peak should sit near 1000G and then be spent
on the riding skill; only studios/RMT hoard beyond that. A configurable
"legitimate savings ceiling" (e.g., 1200–1500G) would let the peak regain its
signal above that level. A soft threshold would be better than a hard cutoff.
The size of the effect depends on the launch economy: if only a few players can
afford the mount, the activity axis can compensate; if most players hold a lot
of gold, the mount's effect on the peak is smaller. The second axis below is
another way to separate the two.

4.3 Activity and the two-axis profile
The current activity factor measures breadth (4 of 7 areas). In CN, composition
is more discriminating: studio farms tend to be combat/dungeon-heavy and
quest-light; normal players are more balanced. We suggest a descriptive
activity profile:
- kills/quests, dungeons/kills, posted/bought, deaths/kills;
- for rate, use Δ between saved observations (the addon already stores them);
- show wealth-for-level × activity composition as two axes, with quadrant
  labels; focus on high wealth/low activity and low wealth/high activity;
- an RMT buyer is unlikely to be a bot, but activity helps judge whether a
  high peak is supported by high activity;
- do not turn it into a second verdict; keep it descriptive.

5. Baselines, validation and privacy
The addon has no communication or uploads (Core.lua:3). A server-wide baseline
would need either a bundled table (median/p90/p95 peak by level band, dated) or
an opt-in aggregate. Without labeled cases, any weighting is a prior; we should
keep the score descriptive, collect community feedback, and not claim a
probability. Over time, aggregated data could refine the rules. Privacy: no
names/GUIDs, no automatic upload.

6. Rollout and open questions
Phase 1: the loot-roll signal, the hover label, and the data questions.
Phase 2: an optional CN profile + baseline robustness + the epic-mount ceiling.
Phase 3: the activity profile and baseline data.
We can test on the CN beta and provide anonymized samples.
Open questions:
- Will 919, repairs, auction spending and potions be available after launch?
- Are the income counters lifetime or windowed? Can the report show it?
- Do you see a workable way to detect advanced riding, or to count vendor
  purchases?
- Would an optional CN profile be acceptable, and which values would you want
  to calibrate first?
```
